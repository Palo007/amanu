Amanu Windows: step 2, both tracks at the same time

2026-11-06 · branch master · commit e79c62b · fork version 0.7.0 · Ryzen 7 5800H (8 cores, 16 logical processors), AC power, Amanu closed, warm runs. Roadmap: docs/roadmap-speed.md, step 2.

Summary

  • Amanu now transcribes the mic track and the call track at the same time. Before, it did the mic first and then the call.
  • The transcripts are identical to step 1: the same segments, text and timestamps.
  • ASR time is 18 % lower on the first test call and 9 % lower on the second one.
  • The goal was 25 % lower. The goal is not met. The change is kept because it is faster and changes no words.

What changed in the code

All code changes are in windows/src/Amanu.App/TranscriptionServices.cs, class LocalTranscriptionEngine.

ItemBefore (step 1)Now (step 2)
Track orderTranscribeAsync called TranscribeFileAsync for the mic, then for the call.TranscribeAsync calls the new TranscribeTracksAsync. It starts every track at the same time and waits for all of them (Task.WhenAll).
ThreadsEach transcribe-cli run used Threads (all 16 logical processors, or AMANU_ASR_THREADS).Each run uses ShareThreads(Threads, tracks): an even share, at least 1. Two tracks on 16 threads get 8 + 8. A recording with one track still gets all 16.
CPU gateEach track took its own CpuTranscriptionGate batch lease.One batch lease covers all tracks. When live transcription starts, it cancels that lease, so both tracks stop at once.
Retry after live preemptionThe track that was stopped ran again from the start.A track that already finished keeps its result. Only the unfinished track runs again. The preemption count shows in transcribe.log.
One track failsThe error stopped the pass.The failed track stops the other track. Amanu reports the real error, not the cancel of the other track.
Output orderMic segments, then call segments, sorted by start time.The same. So the result is identical, also when two segments start at the same time.
Timing logtiming asr.me 99.2 s (convert 0.0 s, 15 runs, preempted 0)The line also shows the threads: timing asr.me 161.1 s (convert 0.0 s, 15 runs, 8 threads, preempted 0). asr.me and asr.them are now times from the common start, so they overlap. asr is the real wall time.

Not changed: the archived audio tracks (only the temporary ASR copy is read), echo removal, the model files, the live worker, and native DLL handling. Each track uses its own temporary folder, so the two runs do not share files.

Test: windows/tests/Amanu.Live.Tests/LocalAsrThreadsTests.cs has a new test for ShareThreads (16/2 = 8, 16/1 = 16, 15/2 = 7, 1/2 = 1, 0 tracks = all threads). All tests pass: 51 live tests and 165 core tests.

Research: how many threads per track?

I tried more threads per track on 1000, with a test build only (the test switch is not in the commit).

Threads per trackThreads in allASR (wall)Words
8 + 8 (kept)16162.7 sidentical
12 + 1224220.7 sidentical
16 + 1632388.1 sidentical
  • More threads than logical processors is much slower. The threads wait for each other and fight for the CPU. 16 + 16 is about 2.4 times slower than 8 + 8.
  • Half the threads per track is the best of the tested counts. The words are the same for all counts.

Why not 25 % faster?

  • In step 1, one track with 8 threads was only about 12 % slower than one track with 16 threads. So one track already uses most of the CPU.
  • When two tracks run at the same time, they share the same CPU time. The gain is only the CPU time that one track left unused.
  • The second call (1021) gained less (−9 %). Its tracks have more pieces (17 runs per track, not 15), and that run was also on a busier computer (echo removal was 139 s, not 121 s).
  • To get more speed, the next steps must do less work or use other hardware, not only use the same CPU in another order: step 3 (call track during echo removal), step 7 (GPU with Vulkan).

Notes for the next measurements

  • dotnet publish -o <other folder> does not copy local-runtime\ and live-runtime\. Copy them from windows\artifacts\publish before you run a test build with -Exe, or the measure run stops after decode.
  • Other sessions measure on the same computer. Use the lock file %USERPROFILE%\Amanu Speed Set\measure.lock: create it before a timed run, delete it after. If it exists, wait.
